# Senior Citizen / PWD discount: ID at sign-up, automatic at checkout

- **Where the ID is given.** Sign-up asks "Are you a Senior Citizen or PWD?" (its own step, after Delivery details), and so does Complete your profile. A yes needs the ID type, number and a front photo (back optional). A Customer who said no, or signed up before this, can send an ID from **Account settings → Senior Citizen / PWD**.
- **What happens to it.** The ID is sent for Staff review exactly as before (`senior_pwd_verifications`, Private Temporary photos, number stored only as a keyed hash, decisions through `/api/internal/senior-pwd/:id/:action`). Sending it never blocks sign-up: if the ID is in use on another account or file-storage is down, the Customer is told and can resend from Account settings.
- **Checkout asks nothing.** Orders from a Customer with an approved, unexpired ID get the discount automatically on one unit of their priciest item. While an ID is pending, declined, revoked or expired, Orders are placed at full price and are never held for the ID check.
- **The rule comes from CREOMS.** `lib/senior-pwd/discount-rule.ts` reads `crms.senior_pwd_discount_settings` (Commerce Settings: percentage or pesos, and a limit in pesos per day, week or month) on every Order placement and on the Checkout page. If the row cannot be read the default applies (5% off, up to ₱125 per week). **The storefront's database role needs SELECT on that table**, as it has for `crms.delivery_settings`; without it the default is used silently.
- **Orders keep their rule.** Each Order saves its discount and the limit and period it was placed under (`orders.senior_pwd_limit_in_centavos`, `senior_pwd_limit_per`, migration `0063`). The cap at confirmation counts the ID's other confirmed Orders in the same Philippine-Time day, week or month and reduces the discount to what is left. Orders from before this change have no snapshot and use ₱125 per week.
- **Same ID number on another account.** The ID number is only ever stored as the keyed hash (`id_hash`); names are not copied, since the account already holds the Customer's name and Staff compare it with the ID in CREOMS. Sending a number that is pending or approved on another account is refused with "This ID is already used on another account" (checked under a per-number lock, so two simultaneous submissions cannot both pass). A number last seen declined, revoked or expired on another account is accepted but flagged: `senior_pwd_verifications.same_id_as_verification_id` points at that other account's latest verification (migration `0064`). CREOMS has no grant on `id_hash`, so this pointer is how it shows "this ID number is already used by another account" and names whose. CREOMS needs `GRANT SELECT (same_id_as_verification_id)` (`docs/db/creoms-senior-pwd-readonly.sql` in the CREOMS repo). Approval still refuses a number already verified on another account.
